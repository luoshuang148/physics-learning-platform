# 后端实习简历与面试准备

## 定位

项目名：Physics Learning Platform（物理教学学习平台）。适合突出 Java 后端工程实践：访问控制、持久化查询、异步流式资源管理和数据保留。不要声称独立从零实现全部原有功能；应明确自己的改进范围，并能对应 Git commit 解释。

## 可选的简历内容

技术栈：Java 21、Spring Boot、Spring Data JPA、MySQL、JWT、OkHttp、SSE、JUnit、GitHub Actions。

> 基于 Spring Boot 开发与完善物理教学平台后端，支持学生答题、教师任务管理和 AI 流式辅导；完善学生注册及教师操作权限，按用户与任务隔离 AI 会话，支持持久化恢复、过期回收和缓存容量限制。
>
> 针对教师答题记录查询的 N+1 问题引入关联预取，并通过 DTO 投影实现有界分页和服务端筛选；在冷持久化上下文、25 道不同题目回归场景中，将旧列表 SQL 数量从 27 条降至 2 条。
>
> 设计请求级 SSE 取消与上游 OkHttp 调用联动，处理同会话重复请求、连接限额及有界执行队列拒绝；将教学任务删除改为归档，通过任务状态机支持并行作业和归档，持久化应参与名单以稳定历史统计，并提供增量升级脚本。
>
> 使用 Maven Wrapper 和 GitHub Actions 建立后端回归、前端构建及 MySQL 新建/升级验证流程，提高项目复现与交付能力。

本轮可替换其中一项：

> 设计任务题目快照和基于用户/请求键的幂等作答，使用事务锁和唯一约束处理重试、归档与旧页面替换冲突；分离首次成绩与补练掌握度，通过数据库聚合支持任务统计，并建立浏览器全流程及 MySQL 迁移、备份恢复验证。

> 为批量学生学情报告设计 RabbitMQ 异步链路：批次、子任务与发件箱在同一事务提交，发布确认后标记投递；消费端手动确认，唯一约束与条件更新认领保证幂等，租约加恢复调度处理实例崩溃；失败按退避重试，耗尽进死信并支持教师手动重试。

一页简历选其中 2–3 点即可。SQL 数值必须带场景；不要写“高并发”“分布式”“百万用户”“性能提升 XX%”或把测试数量当覆盖率。CI 实际通过后再写“通过 CI 验证”。

## 面试需要讲清的内容

| 问题 | 可以结合代码说明 |
| --- | --- |
| 为什么登录保存整行 User 会破坏令牌撤销？ | 登录读到旧 tokenVersion 后，另一请求退出登录；旧实体整体回写可能恢复版本。条件更新 lastLogin 必须匹配版本，资料更新只写脏字段，配合并发回归验证。 |
| 请求超时后为什么不能直接生成新 requestId？ | 服务器可能已提交。发送前保存完整不可变请求，刷新后按相同 requestId 与服务器核对；重试复用同一不可变请求，补练使用独立意图与缓存。 |
| 报告为什么不能先 findAll 再限制条数？ | 完整快照可能包含大图片，限制前已消耗内存。先计数，再分批读取文字投影，限制单字段与 UTF-8 总字节；快照中的空解析也不能用新题库填充。 |
| 鉴权为什么统一到 Spring Security？ | 原来业务接口由 MVC 拦截器认证、Service 里 30 多处手写教师校验，Actuator 又走另一条过滤链。现在 `JwtAuthenticationFilter` 统一认证，通过 Redis 安全快照校验令牌版本、未命中时回库，URL 默认需登录，教师接口用 `@TeacherOnly`（`@PreAuthorize`）在进入控制器前拒绝；Service 只保留“学生只能看自己的数据”这类资源归属判断，并有集成测试约束教师写接口都带注解。 |
| 为什么前端限制教师注册不够？ | 请求可以绕过页面，所以服务端注册持久化前拒绝非学生角色；教师由运营或受保护接口创建。 |
| sessionId 为什么不能单独作为 key？ | 同名 ID 可由不同用户提交；缓存及数据库查询必须包含 userId，任务切换还需要 eventId。 |
| SSE 断开为什么要取消上游？ | 单纯检查布尔标记无法打断阻塞读；注册取消 hook 后，`Call.cancel()` 能中止上游连接。 |
| 为什么还要限制队列？ | 连接限额与执行队列是不同资源；拒绝时也必须关闭 emitter、释放用户与全局计数。 |
| 怎样确认 N+1？ | 制造每条记录不同题目的夹具、清空持久化上下文、统计真实 SQL，避免缓存造成假象。 |
| 并行作业如何保持数据边界？ | V6 已移除单活动任务槽。所有作答、统计、复盘按 eventId 隔离，发布/截止/归档受状态和事务锁保护。名单持久化，停用或新注册不会改写已截止作业的统计。 |
| 归档后数据如何关联？ | 新答题、对话和报告记录 eventId；旧数据无法可靠反推，因此保留空关联。 |
| 为什么引入 Redis？现在能横向扩容吗？ | Redis 共享登录限流、SSE 全局/用户连接名额和 5 分钟认证快照，解决这些状态的单进程限制；同会话单活跃请求、取消路由与题目缓存仍在本地，尚不能声称已完成全量多实例部署。 |
| 登录限流为什么用 Lua？ | IP+用户名 5 次/60 秒、IP 200 次/60 秒的检查、INCR 和首次 EXPIRE 在同一脚本中原子完成，防止并发越限或计数没有过期；成功登录仅清除账号计数。 |
| SSE 实例崩溃会泄漏连接数吗？ | 每条连接持有 60 秒 TTL 租约，每 20 秒续期；用 Redis 时间和有序集合记录期限，准入时原子清理过期名额；完成/超时/错误幂等释放，过期租约不得复活，续期失败关闭流。 |
| 为什么 afterCommit 才失效认证缓存？ | 提交前清除会使并发请求重新缓存数据库旧值，回滚也不应破坏缓存。登出、密码/角色/状态变更与删除在 TransactionSynchronization.afterCommit 失效，返回成功后的请求立即看到新版本；Lua 修订栅栏防止失效前开始的慢查询回填旧快照，事务内读取不写缓存。提交前只写保护标记，失效失败每 5 秒重试，其他实例看到标记回库，避免 Redis 恢复后信任旧快照。 |
| 测试覆盖有什么不足？ | H2 不完全等同 MySQL，另设真实 MySQL 表结构测试；没有生产压力或真实模型吞吐证明。 |
| 消息重复投递如何避免重复保存最终报告？ | `report_batch_items` 唯一约束加 `UPDATE ... WHERE status='PENDING'` 条件认领，只允许一个执行者进入 PROCESSING；完成与失败更新都带 `execution_id` 条件，旧执行者不能覆盖新状态；重复投递会因认领失败直接确认。待处理但长期未认领的任务也会通过 Outbox 恢复；最终结果幂等不等于模型调用恰好一次。 |
| 为什么用 Outbox 而不是创建后直接发消息？ | 数据库事务与消息发布无法原子化：先提交后发消息可能丢投递，先发消息后提交可能让消费者引用不存在的数据。事务内只写发件箱，调度器带租约发布，Broker 确认后才标记投递完成，失败可重投，整体是至少一次投递加幂等消费。 |
| 处理中的实例崩溃怎么办？ | 子任务持有 6 分钟租约（大于 5 分钟模型超时），恢复调度把过期租约重置为可认领并累加尝试次数；新执行者通过条件更新接管，旧执行者的迟到结果无法写入。 |
| 为什么不用 RabbitMQ 延迟插件做重试？ | 避免额外插件依赖和每消息 TTL 的队头阻塞；失败项把状态与下次尝试时间写回数据库，由发件箱按延迟重新投递，进度可查询、可手动干预，重试耗尽则写入死信检查记录并暴露给教师。 |

## 可补充的已实现工程点

- 题库使用轻量投影、服务端分页和搜索，图片与完整选项按详情读取；跨页选题及迟到响应有浏览器回归。
- 应参与名单在发布/加入时持久化，历史统计不随账号停用改变；通过真实 MySQL 并发回归验证最后一位教师保护。
- AI 报告保存输入版本，复用有效结果；区分配置状态与实际调用状态。教学正确率仍须人工评测，不填未经评分的数字。
- 批量报告用 Testcontainers RabbitMQ 做端到端回归：覆盖重复投递幂等、退避重试、死信与租约恢复；MySQL 并发用例验证幂等唯一约束和认领只有一个赢家。

## 展示建议

准备一个自建教师与两个学生，演示注册权限、发布任务、答题、分页筛选、归档与历史仍存在。再展示 SQL 回归测试、阻塞上游取消测试、MySQL 迁移及相关 commit。演示 AI 时使用自己的有效密钥；离线演示可关闭 AI 并解释资源测试使用本地模拟上游。

本轮进一步实现任务不可变快照、预期 ID 原子替换、并发幂等提交、原始成绩与补练分离、JWT 撤销、有界会话恢复，以及浏览器生命周期、MySQL 迁移和备份恢复验证。可用这些具体失败场景及 commit 说明设计取舍。

可继续研究的边界是深分页、多实例协调和真实模型教学质量。能说明这些边界，比堆砌未经实现的技术名词更有说服力。
