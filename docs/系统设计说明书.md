## 1. 系统体系架构描述

### 1.1.1.1 整体架构设计

智学物理系统采用经典的分层架构设计，基于 Spring Boot 3.3.8 构建，整体架构分为表现层、业务逻辑层和数据持久层。表现层基于 Spring MVC 实现 RESTful API，通过 9 个 Controller 处理用户请求，支持 SSE 流式响应技术实现 AI 实时推送。业务逻辑层是系统的核心，包含用户认证、题目管理、答题记录、AI 智能辅导等十大业务模块，各模块通过服务接口解耦，集成 HanLP 中文分词引擎实现错题语义分析。数据持久层采用 Spring Data JPA 框架，配合 MySQL 8.4 数据库存储数据，使用 HikariCP 连接池优化访问性能。

系统后端采用 Java 21 开发，充分利用 Record 类型、模式匹配、Stream API 等新特性。核心框架选用 Spring Boot 3.3.8，整合 Spring Security 6 实现 JWT 无状态令牌认证，通过自定义拦截器实现权限校验和用户信息注入。AI 服务集成方面，系统通过 HTTP REST API 同时对接智谱 AI 和阿里云通义千问两大引擎，通过 OkHttp 实现异步流式响应，两者均基于线程池管理并发请求。为提升 AI 交互体验，系统采用 Spring SseEmitter 实现流式数据推送，配合自主设计的 SessionManager 会话管理器，使用 ConcurrentHashMap 和 ConcurrentSkipListMap 实现线程安全的会话状态追踪。自然语言处理方面，集成 HanLP 中文分词引擎，针对高中物理实验专题定制专业术语词典，优化错题分析的语义理解能力。此外，系统使用 MapStruct 实现 DTO 与 Entity 之间的对象映射，Lombok 简化实体类代码，Hutool 提供工具类支持。

系统采用单体应用部署模式，通过 Docker 容器化技术简化部署流程。应用服务器对外暴露 8080 端口提供 HTTP 服务，数据库服务器运行 MySQL 8.4 实例。系统支持多环境配置管理，区分开发环境、测试环境和生产环境，各环境配置文件独立管理，敏感信息通过环境变量注入。生产环境建议配置 Nginx 反向代理服务器实现负载均衡，同时建议配置 Redis 缓存服务用于缓存热点数据和会话信息。监控方面集成 Spring Boot Actuator，暴露 health、info、metrics 等端点，支持 Prometheus 指标采集。日志系统采用 Logback，配置按日滚动和文件大小限制策略。

## 2. 系统功能结构

### 2.1.1.1 功能模块划分

智学物理系统按业务领域划分为十大核心功能模块。用户认证模块负责用户注册、登录、登出等身份管理功能，采用 JWT 令牌实现无状态认证，区分学生和教师两种角色类型，实施细粒度的接口访问控制。用户管理模块提供用户信息的 CRUD 操作，支持教师查看全班学生信息，学生仅能查看和修改个人信息。题目管理模块实现物理题目的创建、编辑、删除和查询功能，题目内容支持 LaTeX 数学公式格式，包含选项配置、正确答案、题目解析、难度等级、讲解视频映射和图片附件等完整信息。实验配置模块允许教师创建物理实验配置，定义实验名称、描述和有序题目序列，学生按实验流程完成学习，实验与题目智能关联，支持排序管理。

AI 智能辅导模块是系统的核心创新功能，提供实时问答、错题分析和学习报告生成三大能力，集成智谱 AI 和阿里云通义千问双引擎。实时问答功能允许学生向 AI 提出物理学习问题，系统通过 SSE 流式推送 AI 响应，支持上下文连续对话，基于 SessionManager 维护会话状态和交互历史。错题分析功能针对学生答错的题目进行深度解析，AI 会分析错误原因、梳理相关知识点并提供学习建议，支持教师对特定题目发起批量学情分析。学习报告生成功能为每个学生生成个性化的学习分析报告，统计答题情况、正确率、薄弱知识点等关键指标，使用阿里云 Qwen 大模型生成结构化报告文本。教师端还提供班级整体学习情况分析报告和单题作答详情分析，帮助教师了解教学效果并调整教学策略。所有 AI 交互均通过 StreamUtils 统一管理 SSE 连接，防止连接数超限，支持超时回调和异常处理。

答题记录模块记录学生的每次答题行为，包含会话 ID、题目 ID、选择答案、正确性判断、错误原因和时间戳等信息，使用 UUID 作为主键确保全局唯一性。系统支持按用户、会话、题目等多维度查询答题记录，自动生成错题本供学生复习使用，提供词云分析功能展示错误原因的关键词分布。视频管理模块管理教学视频资源，每个视频可关联一道题目，形成"视频学习 - 题目练习"的学习闭环，支持知识点标签和视频时长元数据管理。实验管理模块支持教师创建物理实验配置，定义实验名称、描述和有序题目序列，学生按实验流程完成学习，实验名称和排序序号全局唯一。教师事件模块用于发布全局教学事件，作为时间基准点统一管理教学进度，支持事件的创建、查询和删除操作。错题分析模块基于 HanLP 分词技术对学生自述错误原因进行语义分析，生成可视化词云，帮助教师识别共性问题和教学薄弱环节，针对高中物理实验专题定制专业术语词典和停用词表。

### 3.1.1.2 时序图说明

上述时序图详细描述了学生使用 AI 实时问答功能的完整交互过程。整个流程始于学生在前端界面输入问题并提交，前端应用通过 POST 请求将问题发送至后端 AIController 控制器。控制器接收到请求后，首先从 HttpServletRequest 中获取由拦截器自动注入的 userId 和 sessionId 属性，这些信息在请求到达控制器之前已由身份认证拦截器处理并设置。

随后，控制器调用 ZhiPuAIAssistantService 的参数校验方法，验证请求参数的合法性。验证通过后，控制器调用服务层的 createConfiguredEmitter 方法创建 SSE 发射器，配置 300 秒超时时间。接着，SessionManager 通过 getOrCreateSession 方法获取或创建会话上下文，使用 ConcurrentHashMap 维护会话状态。

接下来，服务层构建 AI 提示词，将学生的原始问题与系统预设的物理学科知识库提示词组合，形成完整的 AI 请求。服务层通过自定义 HTTP Client 向智谱 AI 开放平台发起异步流式请求，AI 服务逐块返回响应内容，服务层通过 SseEmitter 将每个内容片段实时推送至前端，实现打字机效果的流式显示。

流式响应结束后，服务层调用 SessionManager 的 addInteraction 方法，将该次对话记录保存至数据库的 conversation_history 表，同时更新内存中的会话上下文，维护对话历史记录以便后续上下文连续对话使用。最后，服务层完成 SseEmitter，关闭 SSE 连接，前端应用显示完整的 AI 回复内容。

### 4.1.1.2 会话 Token 管理算法伪码

``pseudo
算法: updateTokenUsage
输入: context - 会话上下文, delta - 新增token数
输出: newUsed - 更新后的总用量

BEGIN
    // 原子递增token计数
    newUsed ← context.usedTokens.addAndGet(delta)
    
    // 获取token上限
    maxTokens ← context.maxTokens
    
    // 检查是否超限
    IF maxTokens > 0 AND newUsed > maxTokens THEN
        // 标记会话为不活跃
        context.setIsActive(false)
        LOG_WARNING("会话token达到上限", sessionId, newUsed, maxTokens)
    END IF
    
    RETURN newUsed
END
```

### 4.1.1.3 过期会话清理算法伪码

``pseudo
算法: cleanupExpiredSessions
输入: expiration - 过期时长 (如30分钟)
输出: 无 (副作用: 清理过期会话)

BEGIN
    LOG_INFO("开始清理过期会话", 当前会话总数)
    
    // 计算过期阈值时间点
    expiryThreshold ← LocalDateTime.now().minus(expiration)
    
    markedCount ← 0    // 标记过期计数
    removedCount ← 0   // 移除不活跃计数
    
    // 遍历所有会话
    FOR EACH (key, session) IN sessionStore DO
        // 获取写锁
        session.lock.writeLock().lock()
        TRY
            // 检查是否过期
            IF session.lastActiveTime < expiryThreshold THEN
                session.setIsActive(false)
                markedCount ← markedCount + 1
            ELSE IF session.isActive == false THEN
                // 移除已标记的不活跃会话
                sessionStore.remove(key)
                removedCount ← removedCount + 1
            END IF
        FINALLY
            session.lock.writeLock().unlock()
        END TRY
    END FOR
    
    LOG_INFO("会话清理完成", markedCount, removedCount, 剩余会话数)
END
```

## 6. 接口设计

### 6.1.1.1 RESTful API 接口规范

系统采用 RESTful 风格设计 API 接口，所有接口统一前缀为 `/api/v1`，使用 HTTP 动词表示操作类型。请求和响应数据格式为 JSON，字符编码采用 UTF-8。身份认证基于 JWT Token，通过 Authorization 请求头传递，格式为 `Bearer <token>`。系统通过自定义拦截器 IdentityAuthenticationInterceptor 实现用户身份解析，从 JWT 中提取 userId 和用户类型，并注入到 HttpServletRequest 的属性中，Controller 层直接通过 `request.getAttribute("userId")` 获取。

**HTTP 动词使用规范：**
- GET：查询资源，支持分页和筛选参数
- POST：创建新资源或执行复杂操作（如 AI 问答）
- PUT：完整更新资源（较少使用）
- PATCH：部分更新资源
- DELETE：删除资源

**状态码规范：**
- 200 OK：成功响应（GET、PATCH）
- 201 Created：创建成功（POST）
- 204 No Content：删除成功
- 400 Bad Request：请求参数错误
- 401 Unauthorized：未认证或 Token 过期
- 403 Forbidden：权限不足
- 404 Not Found：资源不存在
- 500 Internal Server Error：服务器内部错误

**会话 ID 传递规范：**
sessionId 不在请求体中传递，而是通过以下方式之一传递，由拦截器自动提取并注入到 HttpServletRequest：
- 请求头：`X-Session-Id: <sessionId>`
- 查询参数：`?sessionId=<sessionId>`

### 6.1.1.2 核心接口概览

**用户认证接口**：提供登录（POST /auth/login）、注册（POST /auth/register）、登出（POST /auth/logout）功能。

**登录标识说明**：支持“用户名 / 真实姓名”两种方式登录，若同一标识既为某用户真实姓名、又为另一用户用户名，则优先匹配真实姓名。

**唯一性约束**：用户名不能与任何真实姓名重复（单向唯一性约束），真实姓名可与用户名重复。

**用户名修改**：用户自助修改用户名时，若实际变更，需校验新用户名不能与任何真实姓名重复。

**AI 智能辅导接口**：实时问答接口（POST /ai/student/realtimeQA）支持学生发起实时 AI 问答，SSE 流式推送响应；错题分析接口（POST /ai/teacher/wrongQuestionAnalysis）支持教师对特定题目发起 AI 学情分析；学生报告生成接口（GET /ai/student/report）为学生生成个性化学习报告。

**答题记录接口**：提交答题接口（POST /answer-records/student/submit）支持学生提交答题记录；查询我的错题接口（GET /answer-records/student/wrong-questions）查询学生自己的错题记录；查询题目错误详情接口（GET /answer-records/teacher/questions/{questionId}/wrong-details）支持教师查看特定题目的学生答错详情；词云分析接口（GET /answer-records/teacher/questions/{questionId}/word-cloud）获取指定题目的错误原因词云分析。

**题目管理接口**：创建题目接口（POST /questions）支持教师创建新题目；查询题目接口（GET /questions/{questionId}）查询单个题目详情；删除题目接口（DELETE /questions/{questionId}）删除指定题目。

**视频管理接口**：创建视频接口（POST /videos）支持教师上传教学视频；查询所有视频接口（GET /videos）获取所有教学视频列表。

**实验配置接口**：创建实验接口（POST /experiments）支持教师创建实验配置；查询实验接口（GET /experiments/{experimentId}）查询单个实验配置；删除实验接口（DELETE /experiments/{experimentId}）删除实验配置。

**教师事件接口**：发布事件接口（POST /teacher-events）支持教师发布全局教学事件；查询事件接口（GET /teacher-events/current）查询当前有效的全局事件；删除事件接口（DELETE /teacher-events）删除当前全局事件。

## 7. 数据库物理设计

### 7.1.1.1 数据库环境配置

系统采用 MySQL 8.4 作为关系型数据库，使用 InnoDB 存储引擎，字符集采用 utf8mb4，排序规则为 utf8mb4_unicode_ci。数据库名为 zhixuewuli，支持事务处理和行级锁机制。HikariCP 连接池配置最小连接数 10，最大连接数 50，连接超时 30 秒，空闲连接超时 10 分钟。JPA 配置批量操作参数：batch_size=25，fetch_size=50，优化大批量数据读写性能。

### 7.1.1.2 核心数据表设计

**用户表 (users)**：存储系统用户的基本信息，支持学生和教师两种角色类型。主键采用 BIGINT 自增 ID，用户名全局唯一，真实姓名也必须唯一便于线下身份对应。设置班级、用户类型和激活状态的组合索引优化查询。预估数据量约 3200 条记录（3000 名学生 +200 名教师）。

**题目表 **(questions)：存储物理题目的完整信息，题目内容统一使用 LaTeX 格式。通过 SHA-256 哈希值实现内容唯一性约束，防止重复题目。包含选项、正确答案、解析、难度等级、视频映射和图片等字段。预估初始题库 500 题，年增量 2000 题，三年累计约 6500 条记录。

**答题记录表 **(answer_records)：记录学生的每次答题行为，使用 UUID 作为主键确保全局唯一性。包含会话 ID、用户 ID、题目 ID、选择答案、正确性判断、错误原因和时间戳等字段。建立多个组合索引优化不同维度的查询。属于高频增长表，预估 3000 万条/年，建议定期归档历史数据。

**对话历史表 **(conversation_history)：存储 AI 对话的历史记录，支持连续的上下文对话。包含用户 ID、会话 ID、问题、答案、序列号、活跃状态、token 数量、会话类型和关联题目 ID 等字段。预估 600 万条/年。

**视频表 **(videos)：管理教学视频资源，每个视频可关联一道题目。包含标题、URL、知识点标签、封面 URL、时长、描述和关联题目 ID 等字段。预估初始 100 个视频，年增量 200 个，三年累计约 700 条记录。

**实验配置表 **(experiments)：支持教师创建物理实验配置，定义实验名称、描述和有序题目序列。实验名称和排序序号均全局唯一。预估初始 20 个实验，年增量 50 个，三年累计约 170 条记录。

**教师事件表 **(teacher_events)：用于发布全局教学事件，作为时间基准点统一管理教学进度。包含教师 ID、教师姓名、事件标题、描述、时间戳和全局事件标识等字段。数据量极少，年约 5 条记录。

**学生报告表 **(student_reports)：存储 AI 生成的学生学习分析报告。包含学生 ID、真实姓名、会话 ID 和报告内容等字段。预估 1.2 万条/年。

### 7.1.1.3 数据库性能优化策略

**分区策略**：答题记录表和对话历史表属于高频增长表，建议按月份进行 RANGE 分区，便于历史数据归档和清理。分区键选择 answered_at 或 created_at 字段。

**读写分离**：生产环境建议配置主从复制，写操作访问主库，查询操作访问从库，提升并发性能。Spring Data JPA 支持通过 AbstractRoutingDataSource 实现动态数据源切换。

**缓存策略**：对于题目、视频、实验配置等低频变化数据，使用 Redis 缓存减少数据库访问。对于答题记录、对话历史等高频数据，使用应用层 SessionManager 内存缓存。用户信息使用@Cacheable 注解缓存到 userCache，过期时间 1 小时。

**索引优化**：所有外键字段建立索引，优化 JOIN 查询。组合索引遵循最左前缀原则，如 idx_user_session_answered(user_id, session_id, answered_at)。避免在索引列上使用函数或计算，防止索引失效。

**备份策略**：每日凌晨 2 点进行全量备份，每小时进行增量备份（binlog），保留最近 7 天的备份数据。使用 mysqldump 或 XtraBackup 工具备份。
