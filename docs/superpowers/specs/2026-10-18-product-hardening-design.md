# Product hardening design

User approved fixing the entire preceding product/software review and retaining commits for each major change. Base e32fefa. Execute inline without another approval round; keep Java 21 / Spring MVC / JPA / MySQL and Vue.

Builder decisions: scope is a single shared classroom, explicitly documented in UI/README; every teacher is an operator in that classroom. No unrequested multi-tenant migration. Preserve legacy records and APIs where possible, while new task submissions require event identity. No business database is modified during implementation.

1. Security/UI: one sanitized Markdown+KaTeX renderer used by all AI output; malicious HTML/links and math regression tests. Remove production account-debug/preview routes and cached account credentials, scrub legacy cache on auth bootstrap, remove self-role/teacher-code UI. Exact public auth paths and health-only monitoring bypass; rate-limit login attempts with bounded local state; invalidate outstanding JWTs on password change and logout using persistent per-user token version. Avoid names/student identifiers in model prompts, production logs and error bodies.
2. Task domain: structured ordered event-question rows containing immutable question/option/answer/explanation snapshots; non-destructive V3 schema upgrade and legacy QIDS conversion. Read task questions from snapshots. Replace/archive operations address expected event ID and use database locks/transaction to avoid stale-tab changes or half-completed replacement. No automatic archive-on-409 in the browser. Server controls UTC timestamp creation; archived task question snapshots remain readable even when bank questions change.
3. Submission: require eventId on task submit, lock/check active task and question membership; validate answer option. Client requestId makes retry idempotent via user+request unique key. Explicit new requestId permits deliberate practice attempts. Store snapshot and return eventId; filter task progress by task+question IDs. Preserve original attempts and determine latest mastery from subsequent attempts.
4. Learning/statistics: task-specific paged records and aggregate counts computed in SQL, separate current-task and cumulative totals. Wrong-book retries navigate to the relevant task question and persist attempts; show resolved/unresolved mastery from latest attempt. Archived-task progress never completes another task. Teacher UI can read archived-task details/reports.
5. AI reliability/quality: bounded history recovery plus aggregate sequence/token accounting; failed history persistence produces an explicit failure, not successful unsaved state. Extract shared Markdown rendering and report input/prompt preparation. Student reports scope by event as well as user/session; report metadata includes scope, sample counts, generation time and model; numerical summaries computed by code. Add a teacher-reviewable fixed evaluation dataset and automated prompt/data invariants, without claiming human approval or real-model accuracy. Capability UI disables generation gracefully when AI is unavailable.
6. Delivery: meaningful browser end-to-end test covers publish/answer/archive/reuse/retry/report no-data scope; CI builds and boots real Docker image with AI disabled and runs database backup/restore smoke test. Add resource/queue/upstream metrics without public detailed monitoring. Add deterministic MySQL benchmark fixture, benchmark script/results with explicit machine/data limits. README/runbooks updated and test evidence recorded per task.

Acceptance: all existing default backend tests and frontend build stay green (old implementation-coupled fixtures updated only with explanation); new boundary regressions fail then pass; real MySQL fresh and V2+V3 upgrade paths tested; independent final review; commits pushed to GitHub with CI outcome checked. External AI evaluation requiring teacher review or paid model credentials remains visibly unvalidated, never fabricated.
